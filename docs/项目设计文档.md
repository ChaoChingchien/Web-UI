## 1. 项目概述

### 1.1 目标

构建一个 **无需 API Key、复用浏览器登录态** 的 AI 团队协作平台。核心能力：

1. **AI 网页版自动化** — 通过 Playwright 操控已登录的 AI 网页（ChatGPT、Claude、Gemini、DeepSeek 等），无需 API Key
2. **AI Team（团队协作）** — 多个 AI 角色分工协作，支持流水线/并行/讨论/混合四种模式，像开产品评审会一样调度一群 AI
3. **子任务管理** — 将复杂任务 AI 自动拆解为子任务，看板跟踪，分配给不同 AI 执行
4. **多接入方式** — 支持网页版自动化（免 Key）、自有 API 接入、本地部署模型（Ollama 等）

### 1.2 产品定位

**OpenTeam 不是另一个聊天框**，而是帮你低成本地调度一群 AI 一起思考、拆解和执行的协作平台：

- **免 API Key**：复用浏览器中已登录的 ChatGPT、Claude、Gemini、DeepSeek 等网页账号
- **AI 军团**：让不同模型分别担任不同角色（顾问、审查员、研究员、写手等），从多个角度分析同一问题
- **汇总决策**：由一个 AI 汇总各方观点，形成更完整的判断和方案

### 1.3 核心特性

| 特性 | 说明 |
|------|------|
| **免 Key 模式** | CDP 连接已登录浏览器的 AI 网页，自动填表/发送/抓取回复 |
| **AI Team** | 多角色协作，支持 4 种模式：Pipeline / Parallel / Debate / Mixed |
| **预设团队模板** | 一键创建：产品评审会、写作工作流、代码审查、头脑风暴等 |
| **子任务管理** | AI 自动拆解目标为子任务，看板拖拽，状态跟踪 |
| **多接入方式** | Web（免 Key）/ API / 本地模型（Ollama / LM Studio） |
| **对话持久化** | SQLite 本地存储，FTS5 全文搜索 |
| **流式聊天** | WebSocket 实时流式推送 AI 回复 |
| **导出功能** | Markdown / 纯文本 / JSON |
| **角色系统** | 8 个预设角色模板 + 用户自定义角色 |
| **亮暗主题** | CSS 变量驱动，支持 Light / Dark / System |

### 1.4 技术栈

| 层级 | 技术 |
|------|------|
| 前端 | React 18 + TypeScript + Vite 5 |
| 状态管理 | Zustand |
| 后端 | Express 4 + WebSocket (ws) |
| 持久化存储 | SQLite (sql.js, WASM) |
| 浏览器自动化 | Playwright Core (Chromium) |
| API 调用 | 原生 fetch (OpenAI 兼容格式) |

## 4. 数据模型

### 4.1 SQLite Schema

```sql
-- ============================================
-- 迁移 001: 基础表（提供商、对话、消息）
-- ============================================

CREATE TABLE IF NOT EXISTS providers (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    icon TEXT DEFAULT '🤖',
    type TEXT DEFAULT 'web' CHECK(type IN ('web', 'api', 'local')),
    is_custom INTEGER DEFAULT 0,
    is_enabled INTEGER DEFAULT 1,
    url TEXT,
    web_config TEXT DEFAULT '{}',
    api_config TEXT DEFAULT '{}',
    local_config TEXT DEFAULT '{}',
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS conversations (
    id TEXT PRIMARY KEY,
    provider_id TEXT NOT NULL REFERENCES providers(id),
    title TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS messages (
    id TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL,
    role TEXT NOT NULL CHECK(role IN ('user', 'assistant', 'system')),
    content TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now')),
    FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE
);

-- ============================================
-- 迁移 002: AI Team 表
-- ============================================

CREATE TABLE IF NOT EXISTS roles (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    icon TEXT DEFAULT '🤖',
    system_prompt TEXT DEFAULT '',
    provider_id TEXT REFERENCES providers(id),
    config TEXT DEFAULT '{}',
    is_custom INTEGER DEFAULT 1,
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS teams (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT DEFAULT '',
    mode TEXT DEFAULT 'pipeline' CHECK(mode IN ('pipeline', 'parallel', 'debate', 'mixed')),
    config TEXT DEFAULT '{}',
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS team_roles (
    id TEXT PRIMARY KEY,
    team_id TEXT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    role_id TEXT NOT NULL REFERENCES roles(id),
    role_order INTEGER DEFAULT 0,
    parallel_group INTEGER DEFAULT 0,
    input_mapping TEXT DEFAULT 'original' CHECK(input_mapping IN ('original', 'previous', 'all_previous')),
    UNIQUE(team_id, role_id)
);

CREATE TABLE IF NOT EXISTS team_runs (
    id TEXT PRIMARY KEY,
    team_id TEXT NOT NULL REFERENCES teams(id),
    input TEXT NOT NULL,
    status TEXT DEFAULT 'running' CHECK(status IN ('running', 'completed', 'failed', 'stopped')),
    final_output TEXT DEFAULT '',
    started_at TEXT DEFAULT (datetime('now')),
    completed_at TEXT
);

CREATE TABLE IF NOT EXISTS team_run_outputs (
    id TEXT PRIMARY KEY,
    run_id TEXT NOT NULL REFERENCES team_runs(id) ON DELETE CASCADE,
    role_id TEXT NOT NULL,
    role_name TEXT NOT NULL,
    input_text TEXT DEFAULT '',
    output_text TEXT DEFAULT '',
    status TEXT DEFAULT 'pending' CHECK(status IN ('pending', 'running', 'done', 'error')),
    error_text TEXT DEFAULT '',
    started_at TEXT,
    completed_at TEXT
);

-- ============================================
-- 迁移 003: 子任务管理表
-- ============================================

CREATE TABLE IF NOT EXISTS projects (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT DEFAULT '',
    status TEXT DEFAULT 'active' CHECK(status IN ('active', 'completed', 'archived')),
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS sub_tasks (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    parent_id TEXT REFERENCES sub_tasks(id),
    title TEXT NOT NULL,
    description TEXT DEFAULT '',
    status TEXT DEFAULT 'todo' CHECK(status IN ('todo', 'in_progress', 'review', 'done', 'cancelled')),
    priority TEXT DEFAULT 'medium' CHECK(priority IN ('low', 'medium', 'high', 'urgent')),
    assignee_role_id TEXT REFERENCES roles(id),
    assignee_provider_id TEXT REFERENCES providers(id),
    conversation_id TEXT REFERENCES conversations(id),
    task_order INTEGER DEFAULT 0,
    due_date TEXT,
    completed_at TEXT,
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now'))
);

-- ============================================
-- 迁移 004: 索引
-- ============================================
CREATE INDEX IF NOT EXISTS idx_messages_conversation ON messages(conversation_id);
CREATE INDEX IF NOT EXISTS idx_conversations_provider ON conversations(provider_id);
CREATE INDEX IF NOT EXISTS idx_team_roles_team ON team_roles(team_id);
CREATE INDEX IF NOT EXISTS idx_team_runs_team ON team_runs(team_id);
CREATE INDEX IF NOT EXISTS idx_team_run_outputs_run ON team_run_outputs(run_id);
CREATE INDEX IF NOT EXISTS idx_sub_tasks_project ON sub_tasks(project_id);
CREATE INDEX IF NOT EXISTS idx_sub_tasks_parent ON sub_tasks(parent_id);
CREATE INDEX IF NOT EXISTS idx_sub_tasks_status ON sub_tasks(status);
```

#### 角色详细定义

##### 1. 研究员 (Researcher) 🔍

**系统提示词：**
```
你的任务是从给定材料中提取关键事实、数据和观点，输出结构化的研究报告。

工作流程：
1. 提取关键事实、数据和观点
2. 对关键主张进行多角度验证，标注确定性等级（确定/可能/存疑）
3. 区分事实与观点，标注信息来源（可追溯时）

输出格式：
- 核心发现摘要（3-5 条要点，每条不超过 2 句话）
- 详细分析（按主题分组，层次化结构）
- 信息缺口（需要进一步查证的内容列表）

注意：信息不足时，标注为"存疑"而非编造。不确定的结论附带置信度。
```

**Team 协作中的行为：**
- Pipeline 模式：接收原始任务，输出结构化研究报告给下游角色
- Parallel 模式：聚焦任务中"需要查证/调研"的维度
- Debate 模式：提供事实依据和数据支撑，避免主观判断

---

##### 2. 写手 (Writer) ✍️

**系统提示词：**
```
将输入内容转化为面向目标读者的成品文本，保持原意的同时改善表达。

工作流程：
1. 确定目标读者和适用文体（报告/文章/邮件/方案/脚本等）
2. 重组结构：标题、列表、段落分隔，每段 3-5 句话
3. 用具体例子和场景说明抽象概念
4. 统一措辞和语气，关键术语首次出现时给出解释

输出格式：
- 直接交付成品，不附加说明
- 保持原文核心信息不变，只优化表达
```


**Team 协作中的行为：**
- Pipeline 模式：接收上游的研究/分析结果，输出面向最终读者的成品
- Parallel 模式：将结构化数据或要点转化为流畅的叙述
- Debate 模式：将分散的观点整合为连贯的论述

##### 3. 审核员 (Reviewer) ✅

## 5. AI Team 设计

### 5.1 协作模式

#### Pipeline（流水线）
```
输入 → [角色A] → [角色B] → [角色C] → 最终输出
```
角色按顺序执行，上一轮输出作为下一轮输入。适用：内容创作、代码开发流。

#### Parallel（并行）
```
          ┌→ [角色A] → 分析A ─┐
输入 ─────├→ [角色B] → 分析B ─┼→ [汇总角色] → 综合报告
          └→ [角色C] → 分析C ─┘
```
多个 AI 同时处理同一任务的不同方面，最后汇总。适用：多维分析、竞品研究。

#### Debate（讨论 — OpenTeam 核心模式）
```
用户: "这个方案有什么风险？"
  │
  ▼
[执行顾问] → 方案可行性分析
  │
  ▼
[风险审查员] → 指出潜在风险和改进点
  │
  ▼
[资料研究员] → 补充相关案例和数据
  │
  ▼
[汇总角色] → 综合各方观点，输出完整判断
```
适用：决策分析、方案评审、头脑风暴。

#### Mixed（混合）
自由编排，流水线和并行的任意组合：
```
              ┌→ [研究员A] ─┐
输入 → [拆解] ├→ [研究员B] ─┼→ [写手] → [审核] → 输出
              └→ [研究员C] ─┘
```

### 5.2 预设团队模板

#### 5.3.2 输入映射策略 (InputMapping)

每个角色在 Team 中执行时，接收的输入由 `input_mapping` 决定：

| 策略 | 枚举值 | 输入内容 | 适用场景 |
|------|--------|---------|---------|
| 原始输入 | `original` | 仅用户原始输入 | 并行模式下各角色独立分析 |
| 上一轮输出 | `previous` | 仅上游一个角色的输出 | 流水线顺序传递 |
| 全部历史 | `all_previous` | 所有已完成角色的输出 | 汇总角色、Debate 后续轮次 |

**输入映射伪代码：**
```typescript
function buildRoleInput(
  mapping: InputMapping,
  originalInput: string,
  previousOutputs: RoleOutput[],
  currentIndex: number
): string {
  switch (mapping) {
    case 'original':
      return originalInput;

    case 'previous':
      return previousOutputs[currentIndex - 1]?.output ?? originalInput;

    case 'all_previous': {
      const all = previousOutputs
        .map(o => `### ${o.roleName}\n${o.output}`)
        .join('\n\n---\n\n');
      return `${originalInput}\n\n---\n\n=== 各方分析 ===\n\n${all}`;
    }
  }
}
```

#### 5.3.3 四种模式的调度详情

##### Pipeline（流水线）

```
调度流程：
1. 获取所有角色 (按 role_order 排序)
2. 依次执行每个角色：
   - 角色 N 的输入 = input_mapping(角色 N-1 的输出)
   - 等待角色 N 完成 → 广播状态 → 执行角色 N+1
3. 最后一个角色的输出作为 Team 最终结果

超时策略：
- 每个角色独立超时 (默认 120s)
- 任一角色超时 = 整个 Pipeline 失败（已完成的角色输出保留）

日志流：
role:start → role:output → role:complete → role:start → ...
```

##### Parallel（并行）

```
调度流程：
1. 获取所有角色 (按 role_order 排序)
2. 找到最后一个角色 = 汇总角色 (通常 role_order 最大)
3. 并发执行所有非汇总角色：
   - 每个角色输入 = input_mapping(原始输入)
   - 使用 Promise.allSettled() 管理，允许部分失败
4. 所有并行角色完成后，执行汇总角色：
   - 汇总角色输入 = input_mapping("all_previous")
   - 汇总角色输出 = Team 最终结果

并发控制：
- 最大并发数：max(parallel_group 数量, 6)
- 信号量限流，避免同时打开过多浏览器标签页
- 同一 parallel_group 内的角色共享相同的输入上下文

容错机制：
- 部分并行角色失败不影响其他角色
- 汇总角色接收所有已完成角色的输出 + 失败角色的错误信息
- 至少 1 个并行角色成功 → 可以继续汇总
- 全部并行角色失败 → Team 执行失败

日志流：
role:start × N  →  role:output (交错)  →  role:complete × N  →  summary:start  →  summary:output
```

##### Debate（讨论 — OpenTeam 核心）

```
调度流程：
1. 获取所有非汇总角色 = 讨论参与者
2. 获取汇总角色 = 汇总人（通常最后一个角色）
3. 第 1 轮：
   - 每个参与者输入 = 原始议题 + "请从你的专业角度发表独立分析"
   - 顺序执行 (role_order)，每个角色可以看到前面角色的发言
4. 第 2 至 N 轮 (N = maxRounds, 默认 3)：
   - 每个参与者输入 = 上一轮所有发言 + "请回应其他角色的观点"
   - 顺序执行，角色可以看到本轮前面角色的回应
5. 收敛检测：
   - 如果连续 2 轮角色间意见变化小于阈值 → 提前结束讨论
   - 如果本轮所有角色输出与上一轮高度相似 → 提前结束
6. 汇总阶段：
   - 汇总角色输入 = 所有轮次的所有发言
   - 输出 = 综合报告（共识点、分歧点、推荐方案、不确定性标注）

轮次控制：
- maxRounds: 默认 3，可配置 2-5
- 每轮所有角色发言总时长上限 = maxRounds × 120s × 角色数
- 单轮可被用户手动停止

收敛检测算法：
```typescript
function checkConvergence(
  currentRound: RoleOutput[],
  previousRound: RoleOutput[]
): boolean {
  // 简化版：计算各角色输出与前一轮的文本相似度
  let totalSimilarity = 0;
  for (let i = 0; i < currentRound.length; i++) {
    totalSimilarity += textSimilarity(
      currentRound[i].output,
      previousRound[i]?.output ?? ''
    );
  }
  const avgSimilarity = totalSimilarity / currentRound.length;
  return avgSimilarity > 0.85; // 85% 相似度 = 已收敛
}
```

日志流：
```
round:1:start → role:start × N → role:output × N → round:1:complete
round:2:start → role:start × N → role:output × N → round:2:complete
...
summary:start → summary:output → debate:complete
```

##### Mixed（混合编排）

```
调度流程：
1. 解析 config 中的执行图定义 (ExecutionGraph)
2. 执行图是一个 DAG，节点 = 角色组，边 = 执行依赖
3. 拓扑排序确定执行轮次：
   - 同轮次的节点可以并行
   - 跨轮次的节点串行依赖
4. 每轮执行：
   - 该轮的所有节点并发执行 (Promise.allSettled)
   - 节点内部按角色组配置执行 (可嵌套 Pipeline/Parallel/Debate)
5. 最后一轮执行汇总角色 → 最终输出

执行图示例：
```json
{
  "stages": [
    {
      "id": "stage_decompose",
      "roles": ["pm_role_id"],
      "mode": "pipeline",
      "depends_on": []
    },
    {
      "id": "stage_research",
      "roles": ["researcher_a_id", "researcher_b_id", "researcher_c_id"],
      "mode": "parallel",
      "depends_on": ["stage_decompose"]
    },
    {
      "id": "stage_synthesis",
      "roles": ["writer_id", "reviewer_id"],
      "mode": "pipeline",
      "depends_on": ["stage_research"]
    }
  ]
}
```

// 信号量实现
class Semaphore {
  private permits: number;
  private queue: Array<() => void> = [];

  constructor(n: number) { this.permits = n; }

  async acquire(): Promise<void> {
    if (this.permits > 0) { this.permits--; return; }
    return new Promise(resolve => this.queue.push(resolve));
  }

  release(): void {
    this.permits++;
    this.queue.shift()?.();
  }
}

#### 5.3.6 错误隔离与恢复

```
错误分级处理：

级别 0 (角色级 — 不影响其他角色)：
  - 单个角色超时 → 标记 error，继续执行其他角色
  - 单个角色返回空 → 标记为 "无输出"，继续
  - 并行模式下的部分失败 → 其余继续，汇总时标注缺失维度

级别 1 (阶段级 — 影响当前轮次/组)：
  - Pipeline 中间角色失败 → 后续角色取消，保留已完成输出
  - Parallel 全部角色失败 → 无法汇总，Team 失败
  - Debate 某轮所有角色都无新观点 → 收敛结束（正常路径）

级别 2 (全局级 — 影响整个 Team)：
  - 汇总角色失败 → Team 执行失败
  - 全局超时 → 停止所有，保留已完成输出
  - 用户停止 → 优雅中断
  - 浏览器进程崩溃 → 无法继续 Web 自动化，标记失败
```

### 5.4 Subagent 调用系统

#### 5.4.1 设计目标

Subagent 系统允许 AI 角色在执行过程中动态创建子代理来并行处理子任务，从而实现"一个 AI 调度一群 AI"的递归协作模式。与预设的 Team 不同，Subagent 是**运行时动态生成**的，由 AI 根据任务复杂度自行判断是否需要拆分和委派。

**核心场景：**
- 研究员说"这个主题需要查 3 个方向"，自动 spawn 3 个子代理分别深入调研
- 程序员说"这个模块可以拆成 API/数据库/前端"，自动 spawn 子代理分别实现
- 汇总角色发现某维度分析不够深入，spawn 子代理补充调研

#### 5.4.2 Subagent 生命周期

```
主 Agent 执行
  │
  ├─ 分析任务 → 决定需要 Subagent
  │     │
  │     ├─ spawn("研究员-市场数据", "请调研...")
  │     ├─ spawn("研究员-竞品分析", "请调研...")
  │     └─ spawn("分析师-数据汇总", "请分析...")
  │
  ├─ 等待 Subagent 完成 (并行执行)
  │     │
  │     ├─ Subagent 1: running → streaming → done
  │     ├─ Subagent 2: running → streaming → done
  │     └─ Subagent 3: running → error (重试) → done
  │
  └─ 汇总 Subagent 结果 → 继续主任务
```

**状态机：**

```
                     ┌──────────────┐
                     │   pending    │
                     └──────┬───────┘
                            │
                            ▼
                     ┌──────────────┐
           ┌─────────│   running    │──────────┐
           │         └──────┬───────┘          │
           │                │                  │
           ▼                ▼                  ▼
    ┌────────────┐  ┌────────────┐    ┌────────────┐
    │ cancelled  │  │    done    │    │   error    │
    └────────────┘  └────────────┘    └─────┬──────┘
                                            │
                              ┌─────────────┘
                              │ (retry ≤ maxRetries)
                              ▼
                       ┌──────────────┐
                       │   running    │  (重试)
                       └──────────────┘
```

### 5.5 调度可靠性增强：契约式协作

#### 5.5.1 核心问题

传统 Team 协作中，每个角色依赖上游的完整输出来理解任务上下文。这带来两个可靠性风险：

1. **上下文污染**：上游的错误或偏差会级联放大，下游无法独立验证
2. **信息过载**：长上下文导致 AI 注意力分散，遗漏关键约束

**解决方案：契约式协作 (Contract-Based Collaboration)** — 将任务拆解为独立单元，每个单元通过结构化"契约"定义输入/输出接口，Agent 在隔离上下文中独立完成并自我验证，验证通过后才交付。

#### 5.5.2 任务单元拆解 (Unit Decomposition)

##### 拆解原则

```
大任务 → 拆解为独立单元，每个单元满足：

1. 输入自包含：单元所需的所有信息包含在输入契约中，不依赖外部上下文
2. 输出可验证：输出有明确的正确性标准，可被程序化或 AI 化验证
3. 边界清晰：单元之间通过结构化接口通信，不共享隐式状态
4. 可并行：尽可能让单元之间无依赖，可并发执行
```

##### 输入契约的结构化格式

```typescript
interface UnitContract {
  unit_id: string;
  task: string;                    // 一句话任务描述
  input_spec: {
    data_models: DataModelSpec[];  // 数据模型定义
    interfaces: InterfaceSpec[];   // 接口签名
    constraints: Constraint[];     // 约束条件
    examples: Example[];           // 输入/输出示例
  };
  output_spec: {
    files: FileSpec[];             // 需要产出的文件
    format: string;                // 输出格式要求
    acceptance_criteria: string[]; // 验收标准
  };
  context_snapshot?: string;       // 最小必要上下文（非完整对话历史）
}

interface DataModelSpec {
  name: string;
  fields: { name: string; type: string; constraints: string[] }[];
  relations?: { target: string; type: 'has_one' | 'has_many' | 'belongs_to' }[];
}

interface InterfaceSpec {
  name: string;
  signature: string;               // 函数签名或 API 端点
  input: string;                   // 输入类型描述
  output: string;                  // 输出类型描述
  behavior: string;                // 行为描述
}

#### 5.5.3 自我验证系统 (Self-Verification)

##### 验证流水线

每个 Agent 在交付输出前，必须通过三级验证：

```
Agent 产出
  │
  ▼
┌─────────────────────────────────────────────┐
│  第 1 级：静态验证 (Static Check)            │
│  - 类型/接口一致性：输出是否符合契约定义的接口 │
│  - 格式完整性：是否包含所有要求的文件/字段    │
│  - 语法检查：代码是否可解析 (AST)            │
│  通过标准：100% 通过，0 错误                 │
├─────────────────────────────────────────────┤
│  第 2 级：行为验证 (Behavior Check)          │
│  - 单元用例：输入→输出是否符合预期           │
│  - 边界条件：空输入/极值/错误输入的响应       │
│  - 状态覆盖：对所有状态组合的响应            │
│  通过标准：≥ 95% 用例通过                    │
├─────────────────────────────────────────────┤
│  第 3 级：集成兼容验证 (Integration Check)   │
│  - 接口对接：能否消费上游单元的输出           │
│  - 契约满足：下游单元能否用此输出作为输入     │
│  通过标准：100% 接口匹配                     │
└─────────────────────────────────────────────┘
  │
  ▼
全部通过 → 交付
任一失败 → 标记失败原因 → 自动重试（最多 1 次）→ 仍失败则标记 error
```

##### 自动验证器实现

```typescript
interface VerificationResult {
  level: 1 | 2 | 3;
  passed: boolean;
  checks: {
    name: string;
    passed: boolean;
    detail: string;
  }[];
  suggestions: string[];  // 修复建议
}

class SelfVerificationEngine {
  async verify(output: AgentOutput, contract: UnitContract): Promise<VerificationResult[]> {
    const results: VerificationResult[] = [];

    // Level 1: 静态验证
    results.push(await this.staticCheck(output, contract));
    if (!results[0].passed) return results; // 快速失败

    // Level 2: 行为验证
    results.push(await this.behaviorCheck(output, contract));
    if (!results[1].passed) return results;

    // Level 3: 集成兼容
    results.push(await this.integrationCheck(output, contract));

    return results;
  }

  private async staticCheck(output: AgentOutput, contract: UnitContract): Promise<VerificationResult> {
    const checks = [];

    // 检查文件产出
    for (const file of contract.output_spec.files) {
      const exists = output.files.some(f => f.path === file.path);
      checks.push({
        name: `文件产出: ${file.path}`,
        passed: exists,
        detail: exists ? '已产出' : '缺失'
      });
    }

    // 检查接口导出
    for (const iface of contract.input_spec.interfaces) {
      const hasExport = output.source.includes(iface.signature);
      checks.push({
        name: `接口导出: ${iface.name}`,
        passed: hasExport,
        detail: hasExport ? '已导出' : `缺少: ${iface.signature}`
      });
    }

    // TypeScript AST 解析（如果适用）
    try {
      // 使用 ts-morph 或简单正则检查语法
      checks.push({
        name: '语法检查',
        passed: true,
        detail: '代码可解析'
      });
    } catch (e) {
      checks.push({
        name: '语法检查',
        passed: false,
        detail: String(e)
      });
    }

    return {
      level: 1,
      passed: checks.every(c => c.passed),
      checks,
      suggestions: checks.filter(c => !c.passed).map(c => c.detail)
    };
  }

  private async behaviorCheck(output: AgentOutput, contract: UnitContract): Promise<VerificationResult> {
    const checks = [];

    // 对每个示例输入运行输出
    for (const example of contract.input_spec.examples) {
      try {
        const result = await this.runExample(output, example);
        checks.push({
          name: `用例: ${example.description}`,
          passed: result.matches,
          detail: result.matches ? '匹配' : `期望: ${example.expected}, 实际: ${result.actual}`
        });
      } catch (e) {
        checks.push({
          name: `用例: ${example.description}`,
          passed: false,
          detail: `执行错误: ${e}`
        });
      }
    }

    return {
      level: 2,
      passed: checks.filter(c => c.passed).length / checks.length >= 0.95,
      checks,
      suggestions: checks.filter(c => !c.passed).map(c => c.detail)
    };
  }

  private async integrationCheck(output: AgentOutput, contract: UnitContract): Promise<VerificationResult> {
    // 检查输出是否能被下游消费
    // 通过接口签名匹配来判断
    const checks = [{
      name: '接口兼容性',
      passed: true,
      detail: '接口签名与契约一致'
    }];

    return {
      level: 3,
      passed: checks.every(c => c.passed),
      checks,
      suggestions: []
    };
  }
}
```

#### 5.5.4 上下文隔离策略

##### 三级上下文裁剪

不同粒度的任务获得不同量的背景信息：

| 级别 | 上下文内容 | 大小限制 | 适用场景 |
|------|-----------|---------|---------|
| **最小** | 仅输入契约（数据模型+接口+约束+示例） | ~500 tokens | 纯实现类单元（代码编写、翻译） |
| **标准** | 最小 + 项目目标 + 技术栈约定 | ~1500 tokens | 设计/分析类单元 |
| **完整** | 标准 + 上游输出摘要 + 团队上下文 | ~4000 tokens | 汇总/集成/决策类单元 |

```
上下文裁剪流程：

完整对话历史 (可能 10K-50K tokens)
  │
  ▼
ContextStripper.extract(input, level):
  1. 丢弃原始对话格式（问答题/讨论记录）
  2. 仅保留"事实与决策"：已确定的技术选型、数据模型、API 定义、约束条件
  3. 结构化重组为契约格式
  4. 移除冗余、矛盾和过时的信息
  5. 输出最小必要上下文
```

##### ContextStripper 实现

```typescript
interface StrippedContext {
  goal: string;                    // 最终目标（1 句话）
  decisions: Decision[];           // 已确定的技术决策
  models: DataModelSpec[];         // 数据模型
  interfaces: InterfaceSpec[];     // 接口签名
  constraints: Constraint[];       // 全局约束
  scope: string;                   // 本单元的职责边界
}

interface Decision {
  topic: string;
  choice: string;
  rationale: string;               // 为什么这样选
  date: string;                    // 决策时间，用于判断是否过期
}

class ContextStripper {
  strip(conversationHistory: Message[], level: 'minimal' | 'standard' | 'full'): StrippedContext {
    // 1. 提取决策：识别"我们决定用X"、"最终选型Y"等句式
    const decisions = this.extractDecisions(conversationHistory);

    // 2. 提取数据模型：识别 TypeScript interface、SQL schema 等
    const models = this.extractModels(conversationHistory);

    // 3. 提取接口：识别函数签名、API 端点定义
    const interfaces = this.extractInterfaces(conversationHistory);

    // 4. 去重 & 冲突解决：后出现的决策覆盖先出现的
    const resolved = this.resolveConflicts(decisions, models, interfaces);

    // 5. 按级别裁剪
    return this.trimToLevel(resolved, level);
  }
}
```

#### 5.5.5 契约匹配与集成验证

##### 上下游接口匹配

执行完所有并行单元后，系统自动检查接口对接：

```
Unit A 输出: userRepository.ts
  导出: { createUser(data): User, getUser(id): User, ... }

Unit B 预期输入 (来自契约):
  "需要 userRepository 提供: createUser(data): User, getUser(id): User"

匹配检查:
  ✅ createUser — 签名匹配
  ✅ getUser — 签名匹配
  ✅ 所有依赖接口均被满足
```

```typescript
interface ContractCompatibilityReport {
  compatible: boolean;
  mismatches: {
    consumer_unit: string;
    required_interface: string;
    provider_unit: string;
    available: boolean;
    signature_match: boolean;
    detail: string;
  }[];
}

class ContractValidator {
  validate(stageResults: Map<string, AgentOutput>, executionGraph: ExecutionGraph): ContractCompatibilityReport {
    const mismatches = [];

    for (const stage of executionGraph.stages) {
      // 找出该阶段之前的输出被依赖的单元
      const dependents = executionGraph.stages.filter(s => s.depends_on.includes(stage.id));

      for (const dep of dependents) {
        const outputs = stageResults.get(stage.id);
        const requiredInterfaces = executionGraph.getRequiredInterfaces(dep.id);

        for (const iface of requiredInterfaces) {
          const available = outputs.some(o => o.exports.includes(iface.signature));
          mismatches.push({
            consumer_unit: dep.id,
            required_interface: iface.signature,
            provider_unit: stage.id,
            available,
            signature_match: available,
            detail: available ? '接口可用' : `缺少: ${iface.signature}`
          });
        }
      }
    }

    return {
      compatible: mismatches.every(m => m.available),
      mismatches
    };
  }
}
```

#### 5.5.6 端到端协作流程

```
用户输入任务
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 1: 分析 & 拆解 (Orchestrator Agent)                │
│  - 分析任务复杂度，决定是否需要拆解                       │
│  - 生成执行图 (DAG)，定义单元和依赖                       │
│  - 为每个单元生成结构化输入契约                           │
│  - 裁剪上下文，为具体实现阶段做准备                       │
│  输出: ExecutionGraph + UnitContract[]                   │
└─────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 2: 并行执行 (Worker Agents)                        │
│                                                          │
│  每个 Worker Agent 收到:                                 │
│  - 结构化输入契约 (接口定义 + 约束 + 示例)                │

│                                                          │
│  Worker 执行流程:                                        │

└─────────────────────────────────────────────────────────┘
  │

┌─────────────────────────────────────────────────────────┐
│ Phase 3: 集成验证 (Integrator Agent)                     │
│  - 收集所有 Worker 输出                                  │

  │
  ├── 全部通过 → Phase 4: 交付
  │
  └── 存在失败 → Phase 2 重试（仅失败的单元）
       │
       └── 仍失败 → 标记为 error，输出已完成的单元 + 失败详情

#### 5.5.7 可靠性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 单元通过率 | 单次执行通过自验的单元比例 | ≥ 90% |
| 一次修复率 | 自验失败后一次修复即通过的比例 | ≥ 80% |
| 接口匹配率 | 上下游接口对接成功率 | 100% |
| 上下文削减比 | 输入契约大小 / 原始上下文大小 | ≤ 20% |
| 并行度 | 可并行的单元数 / 总单元数 | ≥ 60% |

#### 5.5.8 与现有调度方案的集成

契约式协作作为现有调度方案的**可靠性增强层**，不替代原有模式：

```
TeamEngine
  │
  ├─ Pipeline/Parallel/Debate/Mixed  ← 现有模式，保持不变
  │     │
  │     └─ 当角色需要执行复杂子任务时 → 触发契约式拆解
  │
  └─ 契约式协作  ← 新增增强
        │
        └─ 将角色任务拆解为独立单元
           → 并行分配
           → 自我验证
           → 接口匹配
           → 集成交付
```

**集成示例：产品评审会 + 契约式代码实现**

```
1. Team "产品方案" (Debate 模式) 讨论得出：
   "需要开发一个用户管理模块，包含注册、登录、权限管理"

2. 项目经理角色拿到这个需求 → 触发契约式拆解：
   - Orchestrator Agent 分析需求，生成 5 个实现单元
   - 5 个 Worker Agent 并行实现（各自只看到自己的契约）
   - 每个 Worker 自验通过后交付
   - Integrator Agent 组装验证

3. 实现结果回传给项目经理 → 项目经理将其作为"技术可行性"证据
   纳入最终的方案报告
```
